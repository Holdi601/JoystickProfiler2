Device catalog (`DB/Devices`)

From docs/devices.md in the repository (generated, always the current text).

The device catalog says what every DirectInput input of a known simulation device physically is, in one shared vocabulary. Auto Assign uses it to place functions on the right controls. One JSON file per vendor:

{
  "vendor": "VKB",
  "devices": [
    {
      "id": "vkb-gunfighter-mcg-pro",
      "name": "VKB Gunfighter Modern Combat Grip Pro (MCG Pro, with Twist)",
      "kind": "stick",
      "hand": "right",
      "base": "vkb-gunfighter-base",
      "identify": { "vidPids": ["231D:0125"], "names": ["VKB-Sim Gunfighter Modern Combat Pro Twist"] },
      "image": "https://...",
      "sources": ["https://..."],
      "confidence": "medium",
      "axes": [ { "input": "JOY_X", "control": "stick.axis.roll" } ],
      "controls": [ { "input": "JOY_BTN1", "control": "stick.trigger.stage1", "finger": "index", "type": "momentary" } ]
    }
  ]
}
  • id: lower-case slug, unique across all files.
  • kind: stick, throttle, hotas (stick and throttle on one USB id), base (gimbal or FFB base without grip), pedals, collective, yoke, quadrant, panel, mfd, buttonbox, controller (DIY boards), other.
  • hand: right, left, either or none.
  • base: for grips and heads on an exchangeable base. The base has its own entry (kind: base) with its own axes and buttons. Each grip lists the numbers its controls get on that base.
  • identify: USB VID:PID (hex, as Windows reports it) and HID product names. Devices are matched by VID:PID first, then by name. If one product name names a grip exactly, that grip is chosen without asking.
  • image: the manufacturer's own product picture. It is loaded at run time on the user's PC and never shipped. It is only shown when its host is in the file's top-level officialHosts (the vendor's own sites and CDNs). See device-reference.md.
  • productUrl: the official product page.
  • reference (optional): shape (the drawing family) and markers (part id → [x, y], 0..1 of JoyPro's drawing). See device-reference.md.
  • sources: where the numbers come from (manuals, community maps). Facts only, no copied text or pictures.
  • confidence: high (manufacturer manual), medium (community map or default profile), low (control list without verified numbers; such controls have no input).
  • input: JOY_X JOY_Y JOY_Z JOY_RX JOY_RY JOY_RZ JOY_SLIDER1 JOY_SLIDER2, JOY_BTN<n> (1-based) or JOY_BTN_POV<h>_<U|UR|R|DR|D|DL|L|UL>.
  • type: momentary, latched (a switch position that stays), rotary (one encoder step) or analog.
  • label: the printed label of panel switches ("LDG GEAR UP", "ANTI SKID ON"). Auto Assign matches it against the function and its direction.
  • finger: index, middle, thumb, pinky, palm or hand (grip controls only).

#Control vocabulary

N counts left to right, top to bottom. Directions are up|down|left|right|press; 3-way switches use fwd|center|aft or up|center|down.

JOYPRO_DEVICE_KB points the engine to another catalog folder (tests). The user's own definitions in <data>\Devices\*.json (made with the marker assistant or imported, same format) are read after the catalog and replace a shipped model with the same id.

#Replace a device (engine devices replace, devices auto-remap)

JoyPro 1's "replace entire joystick device". Code: engine/EngineDeviceReplace.cs; GUI: MainWindowViewModel.DeviceReplace.cs, Views/ReplaceDeviceWindow.axaml.

  • New ID, same device (new PC, Windows reinstall, other USB port): devices auto-remap [--dry-run] gives a profile device that is not connected the connected device of the same product: same name (letters and digits) or the USB id the profile remembers (JoysticksPGuids), not used in the profile yet. Several connected devices of the kind (a Wooting keyboard's game controller interfaces) are told apart by the inputs the profile uses (axes, highest button, hats); two old devices for one new one, or two that still fit, are left to Replace device. Never another product. The GUI runs it when a profile opens (Engine options "Remap Missing Devices") and shows what moved with Undo. The load correction of profiles saved with another device list (--remap-missing-devices) uses the same rules; before, it took the most similar name among all connected devices, even another product.
  • Replace: devices replace <old> <new> [--mode auto|same|layout] [--map OLD=NEW]... [--merge add|keep|replace] [--grip <device>=<grip id>]... [--dry-run]. auto = same for the same product (same name, USB id or catalog model), else layout. By layout, per input of the old device: the same control id (stick.trigger.stage1), the same id on the other family's device, then each old part goes to one new part of its kind (hat, trigger, lever, brake, ministick, twist ...; the same place in the order first, then the one that has most of its directions; a four-way ministick that reports buttons counts as a hat; POV hats the catalog does not list are hats of their own), buttons in their order as a guess, and last the same input id. Axes only go to axes. A device that is not connected is identified by its name (also "Joystick - HOTAS Warthog" for the catalog's "HOTAS Warthog Joystick") and its inputs come from the profile; unknown devices use the generic layout. Inputs without a target stay on the old device. Modifiers follow their input. When nothing is left on the old device, its name, force feedback and activity follow (picture and USB id only for the same product). The new device already has binds: --merge is required (add both stay, keep the new device's win and the old bind stays on the old device, replace the old device's win and the new device's binds on those inputs are removed). The preview (--dry-run, JSON) lists every input with its part, method, relations, modifiers and the new device's relations on the same input.
  • Checked on the user's old-PC profile (copy): auto-remap moved the same five devices the user had relinked by hand, and the result (502 binds, reformers included) equals that hand-made profile.
  • Remove: devices remove <device> (the device card's Remove) works on one device instance: "Name {GUID}" only with the same GUID. Other devices of the same model (a second unit, the connected one after Windows gave it a new GUID) keep their binds and modifiers (up to 2.2.17 every device of the same name lost them). It removes the instance's binds, its modifiers (also from other devices' binds, which stay), its name, picture, USB id, force feedback and activity. A modifier of another device whose last bind was removed is listed under "Modifiers Without Binds"; the GUI keeps it in the Modifier Library as a temporary modifier. The other bulk deletes of the GUI (delete or merge relations, clear or unbind a bind, Replace with --merge replace) keep such modifiers the same way; only "Delete the ticked modifiers" deletes modifiers. relations mass merge keeps the bind when all merged relations are bound the same (one input, the same modifiers). Smoke check: engine/tests/smoke/deviceremove.ps1.

#Device names (aliases, engine devices alias)

A device can get a name of the user's own ("Left panel"): on the Layout page next to the device's icon (type it, Enter or "Name it"; the x takes it back). It is kept in the profile (JoystickAliases, JoyPro 1's joystick aliases, keyed by the device name with its instance GUID) and shown wherever JoyPro shows a device name: device cards, the bind list and its chips, relation cards, the device filter, the Layout page, Visual Assign, the HUD, the bind picker and the follow-input note (all through DisplayText.ShortDevice). The tooltip keeps the real name ("Left panel - alias of VPC Panel #2 {GUID}"). Settings > Devices > "Device names: show the alias / show the device's real name" (kept in ui-settings.json, showDeviceAliases, default: the alias). Aliases are display only: exports always write the real device.

engine devices alias list
engine devices alias set <device> <alias>
engine devices alias clear <device>

The alias moves with its device (devices auto-remap, exchange, replace); a device that only came back under a new instance GUID shows the alias of the same-named device while that older one is not connected. Older profiles kept the layout template's name there (layout suggest --apply, which no longer writes it); such names are not shown as aliases.
