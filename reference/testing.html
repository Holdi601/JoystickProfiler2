#Test sandbox

No test, gate run or smoke run may write into a real game folder, Saved Games, Documents or JoyPro's own folders of the PC (2.4.3: a test view model's export path defaulted to the real Saved Games\DCS, and "Export first" wrote into the user's Config\Input).

  • Engine. JOYPRO_TEST_SANDBOX=<root> makes the engine refuse every write outside <root>, the temp folder, JOYPRO_DATA_DIR and the folders listed in JOYPRO_TEST_SANDBOX_ALLOW (;-separated). Without its own JOYPRO_DATA_DIR or JOYPRO_LOCALAPPDATA the stand-in %LOCALAPPDATA% is <root>\LocalAppData (data folder <root>\LocalAppData\JoyPro2). A refused write throws before anything is touched, prints [test-sandbox] JOYPRO_TEST_SANDBOX refused ... on stderr, is appended to <root>\sandbox-violations.log (with the stack) and ends the command with exit code 77, also when a catch on the way swallowed the exception. The chokepoint is engine\SandboxedIo.cs: it declares File, Directory, FileStream and StreamWriter in the root namespace JoyPro, so C#'s name lookup takes them instead of System.IO's for every file write of the engine (all namespaces under JoyPro: exports of every game, backups, restore and undo export, strip-defaults and device-luas, sync apply, imports, settings, the support bundle, logs); reads pass straight through (engine\TestSandbox.cs). Picture renders (Image.Save) and zip extraction call the guard themselves. Game settings in the registry (Nuclear Option and Tiny Combat Arena's Unity PlayerPrefs, the registry restore of backups) are never written under the sandbox; JOYPRO_TEST_REGISTRY_ROOT=<key under HKCU> redirects them instead (tests use the fake-registry .json files). A new write in the engine needs nothing extra; only code that spells out System.IO.File / System.IO.Directory bypasses the guard, which only reads may do.
  • GUI tests. TestEnvironment (the module initializer) sets JOYPRO_TEST_SANDBOX to a fresh temp folder for every engine a test starts. The app's default game paths come from Services\UserFolders.cs, which under the sandbox returns stand-in folders inside it (<root>\UserFolders\UserProfile\Saved Games\DCS, Documents, Program Files), and the app does not take over game folders the engine finds on the PC (AdoptEngineGamePaths). Before the first test RealFolderGuard fingerprints (file list, size, time stamp; registry values hashed) %USERPROFILE%\Saved Games, %LOCALAPPDATA%\JoyPro2, %APPDATA%\JoyPro2, %LOCALAPPDATA%\JoyPro and every config location engine games installs finds on this PC; logs, tracks, screenshots and caches are left out. RealFolderGuardTests runs last (RealFolderGuardLastOrderer) and fails the run with the list of changed files, and when any engine of the run logged a refused write. While a JoyPro of the user runs, changes in the JoyPro folders are printed as warnings only. A filtered run without that test checks at process exit and writes the result to stderr and %TEMP%\JoyPro2.Gui.Tests\real-folder-guard-*.txt. SandboxGuardTests proves the refusal: a DCS export into a stand-in folder outside the sandbox and then into the real Saved Games\DCS ends with exit code 77 and changes no file.
  • Smoke test and gate. engine_smoke_test.ps1 runs every engine with its own sandbox and fails when the run's sandbox-violations.log exists. The quality gate runs inside the GUI tests (same sandbox) and allows only its -Out folder besides temp (JOYPRO_TEST_SANDBOX_ALLOW), so its exports can reach only the copies in <Out>\export-copies.

#Speed

Nothing a person waits for should take more than a few seconds (interactive actions ≤ 2 s); the budgets are in gui\JoyPro.Gui.Tests\QualityGate\Budgets.cs and checked by the quality gate's I7.

  • Engine server. The app runs its quick commands (relation editor, catalog, search, binds, layout titles, device and game lists, the DCS export: Services\EngineServerCommands.cs) in one long-running engine serve (engine EngineServer.cs, app Services\EngineServerPool.cs). Every command runs as in a process of its own: own arguments, environment variables, output and exit code, and a fresh copy of the profile as the file has it (EngineProfileCache: the profile is read once and copied per command by ObjectGraphCloner, 15 ms instead of 0.4-1.3 s; after the server's own save the copy is made "as serialized", as a read of the file would give it). A profile older than the DB is corrected on load; the state the DB part of that correction made is kept too (EngineLoadCorrectionCache, per file, DB fingerprint, options and rules version), so the first change after "profile load" does not correct again; the device remap against the connected devices runs every time (serve --self-test compares a kept correction with one that runs and checks that a changed file or DB list runs it again). Kept between commands: the game lists, function map, search and suggestion indexes and the load corrections' lists; before every command the server checks the files they come from (DataStamp: name, size and time of the DB, function and layout catalog files) and answers "stale" when they changed, then the app starts a new one. The app also starts a new server after a refresh or another command that can change game data. Per-run state (backups, diagnostics, detent warnings, device and install detection) is reset before every command. The server warms up as the app starts, ends with the app (closed stdin, the app's process gone) or after 20 idle minutes (JOYPRO_SERVER_IDLE_MINUTES). JOYPRO_ENGINE_SERVER=off runs every call in a process.

  • Checks. gui\JoyPro.Gui.Tests\EngineServerTests.cs runs a sequence of 20 commands (add, show, rename, group, bind, search, browse, suggest, remove, save) once in processes and once in the server and compares output, exit code and the saved profile byte for byte (JOYPRO_SERVER_TEST_PROFILE=<profile> also on a copy of a real profile), a game list changed on disk (a new server answers), and that no server outlives its use. smoke\server.ps1 checks engine serve --self-test (the profile copy serializes to the same bytes as the profile read from the file, also after a save with removed entries and new ones afterwards), the same sequence through engine serve --script and the protocol. Development tools: engine serve --script <file> (one JSON argument array per line, each command timed; JOYPRO_SCRIPT_OUT=<folder> writes every result), engine serve --diff-profiles <a> <b> (where two profiles differ, also in shared instances) and JOYPRO_SAMPLE_OUT=<file> (a sampling profiler of the engine's main thread).

  • DCS export. The input files are read once, several at once (RunFileCache: a file the run wrote is taken from what it wrote, every hit checked by size and time stamp), parsed in parallel and merged in the usual order; the backup manifest is written once per run (a journal in between, read back after a crash); the unique relation name of an import is one lookup. A file that already holds exactly the bytes the export would write is neither backed up nor rewritten (a re-export rewrote and backed up every file, 4 of 5 of them unchanged: most of the time of the gate's export, I7 "dcs export dry-run"); the state record after the export hashes the files from memory, a clean profile's defaults are parsed once per run, and the connected devices are read once per run (the environment log, nuke and the import's device plan each read them again). smoke\dcsexportmodes.ps1 checks that a repeated export rewrites no file and that its undo changes nothing. The output is byte for byte the old engine's (checked on a copy of a real Saved Games folder in merge, merge-overwrite and clean + nuke, and loaded with DCS's own luae.exe).

  • Load corrections. The DB fingerprint hashes only files new or changed since the last fingerprint (<data>\Cache\db-file-hashes.tsv, size and time stamp). A profile saved with an older DB searches a replacement for every action the DB no longer has (CoreInternalDataManagement.cs, FindBestReplacement): each distinct title of the DB is scored once, titles that cannot reach the best so far are dropped by their length and letter histogram, containment only where the letters allow it, and the edit distance is bit-parallel (Myers / Hyyroe). The engine server keeps the prepared lists and every result per DB, so a profile's corrections are searched once (profile load) and not again by the commands after it (Lay out with AI's preview, the Setup wizard's plan, sync diff). The result is exactly the old full search: JOYPRO_CORRECTION_REFERENCE=1 scores every candidate the old way, and the correction reports (--correction-report) of both are compared on copies of real profiles (2298 + 228 replacement searches identical; the user's March 2025 profile 80 s -> 2 s, the first Lay out with AI preview ~100 s -> under 3 s).

  • HUD page live check in OBS. HudObsLiveTests (opt-in: JOYPRO_HUD_LIVE=<folder>) checks the real stream page server started by Start HUD in a sandbox with a fake device stream; tools\obs_hud_live_check.ps1 -Obs adds OBS (portable copy, a copy of the user's OBS settings, Browser Source picture via obs-websocket, the user's %APPDATA%\obs-studio mirrored and restored exactly). docs/hud.md "Live check in OBS".

  • HUD soak (background cost while playing). Everything the HUD runs while the user plays must be unnoticeable (docs/hud.md "Performance"). HudSoakTests (opt-in: JOYPRO_HUD_SOAK=<minutes>, report with JOYPRO_HUD_SOAK_OUT=<folder> -> hud-soak.md; in the quality gate as I12) drives a fake device stream (three devices, every axis moving, reported every 15 ms like the DirectInput poll, a button every half second) with the HUD on and one page of the stream server connected, in three phases: a baseline (the fake devices alone, the HUD off), the stream page only (the player's own HUD off) and the HUD laid out and drawn in a hidden root plus the stream page. It measures the whole test process (so the fake stream and the page reader are in it) after a warm-up: CPU in % of one core, managed allocations, managed heap and working set growth, HUD updates and page events per second, and one frame of the whole HUD drawn in software. Budgets (HudSoak in HudSoakTests.cs): stream page only < 5 % of one core and < 250 KB/s, HUD drawn + stream page < 8 % and < 1500 KB/s, heap growth < 4 MB, working set growth < 40 MB, updates and page events 5 .. 31 a second, a software frame < 12 ms. Measured on the development PC (2026-10-31, 4 minutes, other programs running):

    Measure baseline stream page only HUD drawn + stream page
    CPU (% of one core) 3.87 3.78 2.24
    Allocations (KB/s) 47 58 987
    Managed heap growth (MB) -0.08 0.00 -0.13
    Working set growth (MB) -1.0 -1.5 2.7
    HUD updates / page events per second 0 22.7 22.3
    Stream page data (KB/s) 0 11.4 11.2

    One software frame of the whole HUD: 3.3 ms. The HUD's own share is within the noise of the baseline (the fake stream's timers); the allocations of the drawn phase are Avalonia's layout and drawing of the changed widgets (JoyPro's own path allocates nothing per report: TesterBatch250Tests.Hud_AxisReports_AllocateNothing, HudStreamerTests.Aircraft_... for the aircraft widget). A first 1-minute run showed a working set step of ~49 MB right after the HUD was first drawn (Skia's caches filling); with the warm-up of 30 s it stays at 2.7 MB over 2 minutes.   • HUD tests. #Quality gate

powershell -File tools\quality_gate.ps1 -Profile <profile.pr0file> [-Out <folder>] [-Data user|shipped] [-Only I1,I5] (opt-in, JOYPRO_QUALITY_GATE=1; about an hour on a big profile) runs invariant checks on real data through the real view model and the real engine, in gui\JoyPro.Gui.Tests\QualityGate: the game lists of this PC (a copy of %LOCALAPPDATA%\JoyPro2\GameData) or only the shipped ones (-Data shipped), and always a copy of the profile. It renders its pages in roots that are never shown (HiddenWindow: no window on the desktop, no focus taken) and writes only into -Out; exports run into copies of the game's config or as dry runs, and the real config files are fingerprinted before and after.

Check What must hold
I1 the catalog shows actions for every game and every DCS aircraft (as many as its overview counts); every game chip and DCS aircraft filter of the search shows rows
I2 no catalog title is empty, the id, a lua key, an encoded/hex id, a snake_case identifier, has an unexplained abbreviation ("Rb pitch", ActionTexts.UnexplainedAbbreviation) or is only a word and an axis letter; every action has a category, categories are words (DCS abbreviations are the module's own: a note)
I3 every game of the Start page and Settings > Games has catalog actions, and a title of its own catalog finds it in the search
I4 pitch, roll, throttle, flaps, gear, engine rpm, fire, view, zoom find readable rows (no unexplained abbreviation outside DCS) in every game whose catalog has the word
I5 suggestions of typical relations (pitch, roll, throttle, gear, flaps over two games) are there after the second game's action and after the profile is opened again
I6 every relation of the profile shows readable titles in the editor, the binds peek and the layout table; the check's problems show no raw id (the profile's own relation and device names, whole or quoted, are the user's data; a raw id injected next to one is still caught)
I7 engine server start (a fresh server after the gate's first start; the first start right after the build has its own cold-start budget), profile load, the first Lay out with AI preview after it (rules only), relation open, 200 actions at once, save, suggestions, catalog, search, export per game, the Statistics page's usage stats (1 s) stay within the budgets of QualityGate\Budgets.cs
I8 texts of the main pages have at least 3:1 contrast to their background in Light and Dark
I9 every game the UI names (games list, supported games page, badges, trailer) has an integration, catalog actions and a function map; labels are names, not abbreviations
I10 every page and the relation editor (empty, normal, large relation) at MinWidth, 1280x720 and 1920x1080, 100 % and 150 %, Light and Dark: no overlapping controls or chips, no text drawn over a control or chip it does not belong to, no cut-off text, no pre-filled search that finds nothing; also at 150 % and 200 % text size (Settings > Appearance) and with a serif and a wide font at 150 % text, each with 150 % Windows scaling, in Dark; the Layout page also with the profile's devices as own layouts (long names, "Your layout · N markers" chips; the header names the picture in words, match at most 100 %)
I11 every phrase of engine/tests/fixtures/phrases/phrases.json (names, synonyms, slang, paraphrases, everyday sentences, German) finds its function offline: search box 95 %, catalog filter 90 %, JoyPro assistant 95 %, Manage / Edit with AI 90 %, By description 90 %, search top-row precision 90 %; the app's catalog filter on one phrase and one sentence per function 85 %; failures in phrase-failures.txt
I12 opt-in (-HudSoakMinutes <n> / JOYPRO_QUALITY_GATE_HUD_SOAK=<n>; otherwise a note and no time spent): the HUD and the stream page stay within the HUD soak's budgets ("Speed"), report hud-soak.md

Output: report.md (findings by check, rule and game; timings), findings.json, timings.csv, engine-calls.csv (every engine run with its time) and the pictures of the contrast and layout checks. A finding fails its check; the script's exit code is 0 only without findings.
