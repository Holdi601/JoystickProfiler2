# Falcon BMS 4.38, Falcon 4.0 / Allied Force, Tiny Combat Arena

Tags: **[OBS]** seen in real files of an installed game · **[OBS-bin]** seen in the installed binaries (BMS exe/PDB type info, the launcher 2.4.2.6 assemblies), looked at for interoperability only, nothing modified · **[SRC]** official docs/source · **[INF]** inferred. Research 2026-09-30; BMS had not been run yet, so the generated files below are known from the binaries, not from user files.

## JoyPro integration (`engine bms`, experimental)
- Config path = `<BMS>\User\Config` (found via `HKLM\SOFTWARE\WOW6432Node\Benchmark Sims\*\baseDir` and `X:\Falcon BMS*`, newest first). Two layouts, chosen per export and import:
  - **BMS 4.38.2 and newer (Launcher 3.x)**: `User\Config\JSON` holds `DeviceBindings_*.json` or `KeyboardBindings_*.json`. JoyPro reads and writes only the `DeviceBindings_*.json` files there (see "BMS 4.38.2: the launcher's JSON binding files" below). The launcher builds the `Setup.v100` files, the key files, axismapping.dat, joystick.cal and DeviceSorting.txt from the JSON files whenever it closes or launches, so JoyPro leaves those alone.
  - **BMS up to 4.38.1** (no JSON files): JoyPro edits only the launcher's `Setup.v100.* {GUID}.xml` files; the launcher builds key file, axismapping.dat, joystick.cal and DeviceSorting.txt from them on its next Launch.
  - The legacy key-file workflow is not written.
- Devices are matched by the DirectInput instance GUID in the file name. The launcher writes a device file only after something of that device is assigned in it, so for a connected device of the profile without a file JoyPro creates `Setup.v100.<instance name> {GUID}.xml`: from the launcher's stock file `Launcher\Stock\Setup.v100.<product> {Stock}.xml` when one exists for that model, else empty in the launcher's layout (8 axes, 4 hats x 8 directions x 2 callbacks, 128 buttons x 4 slots). A device that is neither connected nor in a file is skipped; files of devices that are not connected are read with the name from the file.
- Catalog `DB\FalconBMS\actions.tsv` (`engine bms refresh-db [--path <User\Config or key file>]`): visible callbacks (display flag `1`) of the console chapters (`2. LEFT CONSOLE` ... `5. RIGHT CONSOLE` in the F-16 file) and of `MISCELLANEOUS` without its sections SIMULATION & HARDWARE, WINAMP and DEVELOPMENT (F-16: 2.x-5.x, 6.01-6.05, 6.09), plus the launcher's axis functions without FOV and Camera_Distance. The chapters are found by title because the aircraft files number them differently (F-15: consoles 2.-4., miscellaneous 5., views 6.).
- Per aircraft (4.38.2): next to `BMS - Full.key` (F-16) the key file of each further aircraft profile (`BMS - Full-F15ABCD.key`; the profile name comes from `KeyboardBindings_<aircraft>.json` `source_catalog_path`). Its callbacks the F-16 file does not have join the catalog for that aircraft only (sixth column, e.g. `F-15ABCD`); the profiles go into `DB\FalconBMS\aircraft.tsv` (key and title). A new relation with such a callback is limited to that aircraft.
- Buttons: press slot (0); the shift layer is the press+shift slot (1) and becomes a JoyPro modifier `BMS Shift` on the button that holds `SimHotasPinkyShift` (from the export's binds first, else from the files). A modifier on any other button is skipped. Release slots are never imported; clean mode releases cataloged callbacks in them. A new callback gets `Invoke` = Default.
- Hats: `<pov>` string 0 (normal) and 1 (shifted). Top-level lists and the `profileDefaultF16` copy are written alike.
- Axes: `AxisName` on the physical axis, `AssgnDate` = now for a new claim, older claims of the same function are released (unset date `1998-12-12T12:00:00`). Invert, dead zone and saturation are the launcher's steps from the relation's `bms` tuning (see "Every axis, control and force feedback setting" below). Only add never moves a function the game has on another axis (warning); merge and merge-overwrite move it (BMS gives a function to one axis only). An older claim on a device that is not connected stays (the launcher takes the newest claim).
- Export modes: only add writes free slots only; a profile bind on a slot that holds another callback is not written and listed under "Binds Not Written, Button Taken In The Game". Merge replaces such a callback (the conflict) and keeps everything else, also an action's old input. Merge-overwrite also releases the other press slots, hats and axes of connected devices that hold an action the profile binds. Clean releases everything else of the connected devices JoyPro writes, nuke the connected devices without binds in the export. A device that is not connected is never cleared.
- `User\Config\JoyPro.joypro.json` records JoyPro's inputs (no longer used to decide what merge removes). Files keep declaration, whitespace, CRLF and BOM state; only changed files are written (`.jpbak` backup first, read-only attribute restored).
- Refused while `Falcon BMS` or `FalconBMS_Alternative_Launcher` runs (`Launcher.exe` is a generic process name and not checked).
- DB update check: `Falcon BMS.exe` product version + hash of `BMS - Full.key`; new callbacks are named.
- Watcher (`engine sync`): 4.38.2 layout: `JSON\DeviceBindings_*.json`, `Falcon BMS User.cfg`, `Feedback.ini`, `*.pop` (not the `Setup.v100` files the launcher rebuilds on every close); older layout: `Setup.v100.*.xml` and the same three.
- Tested with synthetic device files in the stock layout (smoke test) and the installed 4.38.1 key file. In game 2026-10-09 (`tools\e2e\games\BmsSettings.ps1`, vJoy): 20 of 21 steps, a real Launch after an export included (the launcher built its files from JoyPro's, Setup > Controllers showed the exported axes); entering an active cockpit failed (an earlier settings run: 20/26, trim calibration). Not yet tested: a device file the launcher wrote for a real (physical) device, and the flight part.

### BMS 4.38.2: the launcher's JSON binding files
Seen in a real 4.38.2 config (`Bin\x64\Falcon BMS.exe` 4.38.2, Falcon BMS Launcher 3.0.2) [OBS]:
- On its first start the launcher imports the older files once (`User\Config\Launcher-Backups\V2-to-V3-Import-<date>_<time>\` keeps the files it read; its log `User\Config\Launcher_Log.txt` says "Legacy import skipped because existing Launcher JSON bindings were found" on every later start). From then on the JSON files are the launcher's store: when it closes or launches it writes `BMS - Auto.key`, `BMS - Auto-F15ABCD.key`, `DeviceSorting.txt`, every `Setup.v100.*.xml`, `axismapping.dat`, `joystick.cal` and the pilot file from them. Changes written into those files by hand or by an older JoyPro are replaced then.
- Aircraft profiles: `F-16` and `F-15ABCD` (the launcher's Controls page has a Profile list). Key files per profile: `BMS - Full.key` and `BMS - Full-F15ABCD.key`; the launcher's outputs `BMS - Auto.key` and `BMS - Auto-F15ABCD.key`.
- `JSON\DeviceBindings_<aircraft>_<VIDPID>_<device name>.json`, one per device and aircraft profile, for every device the launcher has seen (also with nothing bound). The device name is the instance name with characters a file name cannot hold replaced by `_` (`MFG Crosswind V2/3` → `MFG Crosswind V2_3`). UTF-8 without BOM, CRLF, two-space indent, `"name": value`, an empty list as `[` and `]` on two lines, a line end after the last brace. Members in this order: `schema_version` (2), `binding_type` (`hotas`), `durable_device_key` and `pidvid` (VID and PID as 8 hex digits, VID first: `346E1000` for VID 346E, PID 1000), `product_name`, `instance_name`, `vendor_id_hex` / `product_id_hex` (`1000` / `346E` for that device: PID and VID, the other way round than the names say), `duplicate_pidvid_sequence_number` (null), `axis_count`, `button_count`, `pov_count`, `capabilities_read_successfully`, `last_seen_instance_guid` (lower case, with braces), `aircraft_profile`, `axis_binding_scope` (`shared_currently_f16_wins_if_files_differ`), `axis_bindings`, `button_bindings`, `pov_bindings`.
- `axis_bindings`: 30 entries, one per launcher axis function (`logical_axis_name`: Pitch, Roll, Yaw, Throttle, Throttle_Right, Toe_Brake, Toe_Brake_Right, FOV, Trim_Pitch, Trim_Yaw, Trim_Roll, Radar_Antenna_Elevation, Range_Knob, Cursor_X, Cursor_Y, COMM_Channel_1, COMM_Channel_2, MSL_Volume, Threat_Volume, `intercom`, AI_vs_IVC, HUD_Brightness, FLIR_Brightness, HMS_Brightness, Reticle_Depression, Camera_Distance, HSI_Course_Knob, HSI_Heading_Knob, Altimeter_Knob, ILS_Volume_Knob) with `physical_axis_index` (null = not assigned, 0..7 = X, Y, Z, Rx, Ry, Rz, Slider 1, Slider 2), `saturation`, `deadzone`, `curve` (1), `center_offset` (0), `invert`; the Throttle entry also has `afterburner_detent` and `idle_detent` (null). The axes are shared by all aircraft: the launcher writes the same values into every aircraft file of the device, and the F-16 file counts when they differ. Unassigning an axis in the launcher sets `physical_axis_index` null and saturation/deadzone None, curve 1, invert false.
- `button_bindings`: one entry per bind, `button_index` (0-based), `assignment_index` (0), `shift_state` (`Unshifted`), `trigger` (`Press`), `callback_name`, `invoke` (`Default`), `sound_id` (0). A button without a bind has no entry. Per aircraft: the F-16 and the F-15 file of a device hold different binds.
- `JSON\KeyboardBindings_<aircraft>.json`: `schema_version` 2, `binding_type` `keyboard`, `aircraft_profile`, `source_catalog_path` (the full path of the aircraft's `BMS - Full*.key`), `rows` (every key-file line with `callback_name`, `description`, `category_name`, `section_name`, key and chord scancodes and modifiers, `visibility`, `row_kind`, `is_modified`). JoyPro does not write them.
- What JoyPro does with them: import reads the axes from the F-16 file and the unshifted press binds of every aircraft file; a bind found in every aircraft whose key file has its callback is a bind for all aircraft, else it is limited to the aircraft it was found in. Export writes each relation into every aircraft whose key file has the callback (a relation limited to aircraft only into those), and an axis into every aircraft file of the device; the same axis function on another connected device and another function on the target axis are unassigned like the launcher does (on a device that is not connected: left, with a warning). New entries look like the launcher's (`assignment_index` 0, `Unshifted`, `Press`, `invoke` Default, `sound_id` 0), in `button_index` order. A file JoyPro does not change is not written; a changed one keeps the layout above byte for byte (`.jpbak` and versioned backup first). Clean releases the axes JoyPro does not set on the connected devices it writes (in every aircraft file) and the unshifted press binds it does not set in the aircraft files it writes buttons into (an aircraft file of the device without a button of the profile keeps its binds); nuke empties every aircraft file of a connected device the profile does not use; merge-overwrite releases the inputs holding an action the profile binds elsewhere. A device is found by `last_seen_instance_guid`, else by VID:PID when one device of that model is connected.
- Not seen in a file yet, so JoyPro does not write it and says so in the export result: hat binds (`pov_bindings` was empty in every file), the shifted layer and release binds (any `shift_state` other than `Unshifted` or `trigger` other than `Press`), the throttle detent values, and dead zone / saturation values other than `None` (JoyPro writes the step names None, Small, Medium, Large of the launcher's XML files; **UNVERIFIED** for the JSON files). Entries of these kinds stay as they are in every export mode. A file with another `schema_version` is left alone with a warning.
- No `DeviceBindings_*.json` yet (the new launcher was not started with the devices connected): the export stops and says to start the launcher once with the devices connected.

- One-sided functions (no dead zone): Throttle, Throttle_Right, Toe_Brake(_Right), HUD/HMS/FLIR brightness, Reticle_Depression, the volumes (COMM 1/2, MSL, Threat, Intercom, AI vs IVC), FOV, Camera_Distance, the HSI/altimeter knobs. A stored dead zone there (old setups) acts around the middle of the travel; the export resets it to None with a warning.
- User.cfg: an existing `set` line above the marker is changed in place (all copies); a new one goes right before the marker as `set g_x v // JoyPro`, in the launcher's normal form (it collapses spaces and drops lines containing `// LAUNCHER OVERRIDE` / `// SETUP OVERRIDE`). The launcher itself only writes g_nButtonsPerDevice, g_nHotasPinkyShiftMagnitude, g_nNumOfPOVs/g_nPOV*, g_bExportRTTTextures and the VR cfg's lines into its block, none of JoyPro's keys. CRLF, UTF-8 without BOM (BOM kept if present). A curve value of 0 adds no line. Merge and only add keep a curve value the user changed in User.cfg (warning); the game-wide settings are always written.
- The curve lines are written only for values a tuning sets (import or `binds tuning set`); a tuning inherited from the base (fit) sets the launcher steps (nearest to the base dead zone / saturation; a slider's saturation is converted from whole to half travel) but **no** exponent: the forum calls BMS's curve "very aggressive", so DCS curvature is not converted until the formula is measured.
- Import: steps, invert and one-sided flag from the device XML, `axisExp`/`axisSat` from User.cfg (lines above the marker) of the five curve axes; stored as the relation's `game:FalconBMS` tuning (not the base DCS uses). Game-wide settings are not imported (as for the other games).
- An export without BMS binds still writes the game settings and detents (`IGameSettingsExport`).
- Preview (`binds tuning preview --game FalconBMS`): u = |x| (after invert); 0 inside the dead zone (int/10000 of the half travel), 1 from the saturation (int/10000; None = 1), linear between, as DirectInput applies `DIPROP_DEADZONE`/`DIPROP_SATURATION` (also on one-sided axes, around the centre of the physical travel); then `axisSat`: v = min(1, v / (1 - s/100)) ("percentage to reduce the physical stick travel required to reach 100 %"), then `axisExp`: v = (1 - e) v + e v³ with e = exp/100 ("blend from fully linear (1) to a cubic curve (99)"), both quoted from BMS forum moderator airtex2019. **UNVERIFIED**: whether BMS reads 9500 as full output at 95 % (file ints, DirectInput meaning) or 99 % (User Manual / launcher preview "1 %"); the exp formula (the same moderator also called it "very aggressive, 2-3 recommended", which a linear-cubic blend is not); the order of DirectInput and cfg shaping; what `g_fFlightControlsDeadband` does (not in the preview).
- Not implemented: Enable Custom Axis Shaping (pop byte 409) with `axiscurves.cal` (header fields `dwObj`/`dwHow`, axis order and how BMS applies the points are unverified; no BMS-written sample exists); raw non-step dead zone ints (only possible with "Launch without any Setup override"); the in-sim step sizes `g_nDeadzone*`/`g_nSaturation*`; Roll-linked NWS (the launcher rewrites pop byte 410 from its own checkbox on every Launch); undocumented cfg values (`g_nFFEffectAutoCenter`, `g_bFFCenterFix`, `g_nThrottleMode`, smoothing).
- In game (2026-10-09: 20 of 21 steps; entering an active cockpit failed, so the sweeps did not run): `tools\e2e\games\BmsSettings.ps1` exports random steps/invert for the three trim axes, a pitch curve, detents and FFB settings, presses Launch through UI Automation, checks what the launcher generated (step ints in axismapping.dat, detents in joystick.cal, JoyPro's User.cfg lines still above the block, pop byte 388) and then sweeps vJoy: the trims through shared memory (`FalconSharedMemoryArea` FlightData.TrimPitch/Roll/Yaw, offset counted from `Tools\SharedMem\FlightData.h`; BMS exports no stick position, so pitch's exponent is captured from the `g_bDisplayAxisValues` overlay by screenshot/OCR for a manual fit). Snapshot/restore of User\Config, theater.lst, the test pilot and the launcher's side folders.
### Telemetry recording (`gui/JoyPro.Ffb.Core/Telemetry/Bms/BmsTelemetry.cs`)
- Source: BMS's shared memory, its official export interface for cockpit builders and tools (`Tools\SharedMem\FlightData.h`), not the game's process memory. `FalconSharedMemoryArea` (FlightData, v118), `FalconSharedMemoryArea2` (FlightData2, v23) and `FalconSharedMemoryAreaString` (StringData) are opened with read rights only; nothing is ever written. Until BMS has created them the feed retries every 2 s ("BMS has not opened its shared memory (it does so when it starts)"); then it polls at 20 Hz on a timer, copies both structs into reused buffers and publishes a frame only when they changed. The string area is re-read only when FlightData2.StringAreaTime changes.
- Session = in 3D: FlightData.hsiBits `Flying` (0x80000000). Entering 3D raises session start, leaving it (or the feed stopping) session end; in the UI no frames are published.
- Keys `bms.*` in the game's own units (ft, ft/s, kt, rad, lbs, %), grouped by category: position/velocity, attitude, air data, engine (and engine 2), fuel, gear and surfaces, lights (the bit words plus every named bit as 0/1), instruments (HSI/ADI/altimeter/RALT), trim, countermeasures/ECM, RWR (count + per active contact symbol/bearing/activity/launch/selected/lethality/new/jamming), radio/navigation/IFF, electrics/hydraulics, head offsets, RTT export rectangles, session (versions, ACD index, time of day, MP pilot states) and derived `bms.calc.*` (true heading 0..360, ground track, ground speed, altitude, vertical speed ft/min, total fuel, AGL while RALT is valid, bullseye bearing/range). FlightData2 members newer than the running BMS's FLIGHTDATA2_VERSION are left out.
- Events: `bms.ded` / `bms.pfl` (5 lines joined by `\n`, at most 4 per second), `bms.pilots` (MP list, `callsign|state` per line), objects snapshot with the bullseye and the steerpoints/markpoints/pre-planned threats of the string area (lat/lon linearised around the ownship, u/v exact in sim feet converted to m). Session facts: aircraft (StringData AcName, else "ACD n"), map (ThrName), pilot (the callsign when the pilot list holds one name), `bms.flight` (flight callsign from VoiceHelpers), game version.
- A test re-derives every offset from the installed `FlightData.h` (skipped without BMS), so a BMS update that moves a member fails the build's tests.
- Not available in shared memory: other aircraft, ground units and weapons (only RWR bearings, no positions), throttle/stick positions, flaps as 0..1.

- Smoke test: `engine\tests\smoke\bms.ps1` with fixtures from the stock files (`fixtures\bms\settings`: stock User.cfg + a launcher block, stock Feedback.ini, the launcher's new-pilot .pop).
- Smoke test of the 4.38.2 layout: `engine\tests\smoke\bmsjson.ps1` with `fixtures\bms-json\Config`: JSON files of a real 4.38.2 config with the smoke devices in place of the real ones, lines of both key files, a `Setup.v100` file that must stay as it is. It builds its own command list from those key files (refresh-db), then checks scan, import, a byte-identical round trip, per-aircraft writing, axis moves, merge-overwrite, clean, the watcher and the missing-files message.

## Falcon BMS 4.38.1 (`C:\Falcon BMS 4.38`)

### Who owns which file
- 4.38 ships the "Alternative Launcher" (`Launcher\FalconBMS_Alternative_Launcher.exe`, .NET WPF). `Hotas\README.TXT`: "PLEASE USE THE NEW LAUNCHER EXPERIENCE TO DEFINE KEYBOARD AND HOTAS MAPPINGS." [OBS]
- **Launcher-managed (default):** the truth is one `User\Config\Setup.v100.<SanitizedProductName> {<INSTANCE-GUID>}.xml` per device plus the keyboard lines of `BMS - Auto.key`. On every Launch the launcher regenerates `axismapping.dat`, `joystick.cal`, `DeviceSorting.txt`, the override block of `Falcon BMS User.cfg`, `BMS - Auto.key` / `BMS - Auto-F15ABCD.key` and the key-file name in `<callsign>.pop` (unless "Launch without any Setup override" is ticked). [OBS-bin]
- **Legacy:** hand-edited key files / in-sim Setup (writes `axismapping.dat` + `joystick.cal` on OK; saving key files there drops all comments). [SRC TM 10.1.1, 10.7.5]

### Files (`<BMS>\User\Config\`)
| File | Format | Role |
|---|---|---|
| `*.key` | text | callbacks → keyboard keys, DX buttons, POV hats |
| `<name>-F15ABCD.key` | text | separate profile for the F-15 |
| `DeviceSorting.txt` | text | DirectInput device order = device index |
| `axismapping.dat` | binary, 504 B | device/axis per in-game axis, deadzone, saturation |
| `joystick.cal` | binary, 720 B | per-axis used/reversed, throttle detents |
| `<Callsign>.pop` | binary, 468 B | pilot options incl. active key file (`char[32]` at +336) |
| `Falcon BMS.cfg` / `Falcon BMS User.cfg` | `set g_x value` | User.cfg overrides; launcher appends its override block |
| `Setup.v100.* {GUID}.xml` | XML (XmlSerializer, UTF-8 no BOM) | launcher's per-device store |
| `DeviceSuppress.txt` | `{GUID}` per line | devices the launcher ignores |

### Key-file grammar [OBS stock files; OBS-bin launcher regexes; SRC TM 10.5]
Stock files: ASCII, CRLF, no BOM (archive files contain CP1252 bytes; launcher writes Auto.key as UTF-8 LF). Read as Latin-1, keep line terminators. Classify: comment `^\s*#`; DX/POV line when the 4th token is `-2` (button) / `-3` (POV); else keyboard line.

- **Keyboard (9 fields):** `AFGearToggle 119 0 0x22 0 0 0 1 "GEAR: LG Handle - Toggle"` = callback, soundId (-1 none), 0, scancode hex (`0XFFFFFFFF` unbound; `0X`/`0x` mixed), modifiers (Shift 1, Ctrl 2, Alt 4), combo key, combo modifiers, display flag (`1` visible, `-1` headline, `-0` locked — keep the text, not an int, `-2` hidden), `"description"`.
- **DX button:** `SimTriggerFirstDetent 0 -1 -2 0 0x0 -1` = callback, buttonId, invoke (-1 default, -2 down, -4 up, 8 UI), `-2`, pressRelease (0 press, 0x42 release), `0x0`, [soundId], ["desc"].
- **POV:** `AFElevatorTrimUp 0 -1 -3 0 0x0 0` = callback, pov (0/1 = hats 1/2 unshifted, 2/3 shifted), -1, `-3`, direction 0-7 clockwise from up, `0x0`, [soundId]. Unmapped hat directions pan the view; map `SimDoNothing` to block.
- Same DX id twice → only the last line fires. Shift layer: `SimHotasPinkyShift` on id and id+offset; one shift layer for all devices.

### Numbering
- Button id = `deviceIndex * g_nButtonsPerDevice + (button - 1)`; deviceIndex = 0-based line in DeviceSorting.txt (keyboard not counted); default 32 per device, shifted = id + `g_nHotasPinkyShiftMagnitude` (stock 256). The launcher writes `g_nButtonsPerDevice 128` and shift magnitude `N*128` (N devices). [SRC TM 10.8.4; OBS-bin]
- POV devices: `g_nNumOfPOVs`, `g_nPOV1DeviceID`, `g_nPOV1ID`, `g_nPOV2DeviceID`, `g_nPOV2ID`; device ID = DeviceSorting position + 2 (0 mouse, 1 keyboard). [SRC TM 10.8.3; OBS-bin enum device_t]

### DeviceSorting.txt
`{PRODUCT-GUID} "Sanitized Product Name"` per line, e.g. `{0402044F-0000-0000-0000-504944564944} "Joystick - HOTAS Warthog"` (PIDVID product GUID, not the instance GUID). The launcher rewrites it in DirectInput enumeration order minus DeviceSuppress. Name sanitizer: `[^A-Za-z0-9\~\`\[\]\{\}\-_\=\'\x20]` removed.

### axismapping.dat (504 B, little-endian) [OBS-bin PDB]
```
+0  int32 FlightControlDevice (device_t of the Pitch device; 1 = keyboard when unassigned)
+4  GUID  FlightControllerGUID (instance GUID, Guid.ToByteArray layout)
+20 int32 totalDeviceCount
```

Deadzone None/Small/Medium/Large = 0/100/500/1000; saturation = -1/9500/9000/8500; unassigned record `FF FF FF FF FF FF FF FF 64 00 00 00 FF FF FF FF`. Invert lives in joystick.cal. Wrong sizes are rejected by BMS.

### joystick.cal (30 × 24 B) [OBS-bin]
`{ int32 center; int32 cutoff; int32 ioVal; int32 smoothingFactor; float engrValue; bool isUsed; bool isReversed; pad[2] }` in `GameAxis_t` order (Pitch, Roll, Yaw, Throttle, Throttle2, TrimPitch, TrimYaw, TrimRoll, BrakeLeft, BrakeRight, FOV, AntElev, CursorX, CursorY, RangeKnob, CommVol1, CommVol2, MSLVol, ThreatVol, HUDBrightness, RetDepr, Zoom, IntercomVol, HMSBrt, AIvsIVCVol, HUDFlirBrightness, HSICourse, HSIHeading, Altimeter, ILSVol) — not the axismapping order. Launcher default: center 0, cutoff 15000.

### Launcher XML `Setup.v100.<name> {<INSTANCE-GUID-UPPER>}.xml` [OBS stock; OBS-bin]
Root `<JoyAssgn>`; children in order: `<detentPosition><AB/><IDLE/>` (0..65536), `<axis>` 8 × `<AxAssgn>` for X,Y,Z,Rx,Ry,Rz,Slider0,Slider1 (`<AxisName>` Roll/Pitch/Yaw/Throttle/Throttle_Right/Toe_Brake/Toe_Brake_Right/Trim_*/…, `<AssgnDate>` — newest claim wins, `<Invert>`, `<Saturation>`/`<Deadzone>` None|Small|Medium|Large), `<pov>` 4 × 8 directions × (unshifted, shifted) callbacks, `<dx>` 32 or 128 × 4 slots (press, press+shift, release, release+shift; empty = `SimDoNothing`; `<Invoke>` Default|Down|Up|UI). 2.4.x adds `<profileDefaultF16>` (wins over top-level dx/pov when it has 128 entries) and `<profileF15ABCD>`.

### Exporter recommendation
1. Refuse while `Falcon BMS`, `FalconBMS_Alternative_Launcher` or `Launcher` runs; back up; restore read-only attributes.
2. Launcher-managed (any `Setup.v100.*.xml`, or the pop's key file is `BMS - Auto`): edit only the device XMLs (`<dx>`/`<pov>` slots, the `profileDefaultF16` copy, `<axis>` entries with a newer `AssgnDate`); never the generated files.
3. Legacy: edit only DX/POV lines of flight callbacks (e.g. a `# ==== JoyPro BEGIN/END ====` block) and the affected records of `axismapping.dat` / `joystick.cal` after checking sizes 504/720.
