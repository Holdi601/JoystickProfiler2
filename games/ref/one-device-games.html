The game page in plain words: ACE COMBAT, Battlefield, Hell Let Loose: Vietnam, Other games (documented only). Full matrix: Game support. What an export does in this kind of game: Export flow, in the game.

From docs/games/one-device-games.md in the repository (generated, always the current text).

Some games take only one joystick (Battlefield) or only Xbox controllers / XInput (Hell Let Loose: Vietnam, ACE COMBAT 8). A HOTAS of several devices then works only through JoyPro's virtual mode (docs/virtual-joystick.md):

  • vJoy target (DirectInput, one virtual joystick): for games that read one DirectInput device. JoyPro merges the inputs the game's relations use onto one vJoy device, exports the binds to it, and HidHide hides the real devices from the game.
  • Xbox pad target (XInput, one virtual Xbox 360 pad through ViGEmBus): for games that only read XInput. It has two sticks, two triggers, 14 buttons and the D-pad. JoyPro follows the game's own gamepad layout where it knows it, gives the rest in order, and lists what does not fit.

The engine marks these games with IGameDeviceLimit (engine/Games/GameIntegration.cs):

Field What it does
MaxJoysticks Joysticks the game reads; 0 = XInput only
SuggestedMode virtual or xbox
DeviceLimitNote One sentence for the user
AvoidVJoyAxes vJoy axes the game must not see

The marking is used in four places:

  • engine vjoy status shows "one-device game: suggested" for such a game in native mode.
  • engine vjoy mode <game> native warns.
  • The Virtual Joystick page shows the suggestion with a "Use it" button.
  • An export in native mode warns when the binds use more joysticks than the game reads.

#Template: adding a one-device game

  1. Detection: Steam app id / registry key, process names (for the watcher, auto start and HidHide's block list), the settings path(s), Steam Cloud (steam_autocloud.vdf) or server-synced variants.
  2. Input capability: DirectInput yes/no, how many devices, the limits (buttons, hats, axes), whether a device with Rx/Ry is taken for a gamepad; XInput yes/no; GameInput.
  3. Target: vJoy (DirectInput binds writable), Xbox pad (XInput only; use the game's gamepad layout), or document only. Implement IGameDeviceLimit (MaxJoysticks, SuggestedMode, DeviceLimitNote, AvoidVJoyAxes) so status, GUI and export suggest the virtual mode.
  4. Catalog (DB\<Game>\actions.tsv, built by engine <game> refresh-db from the game's own files): the flight actions; for an Xbox game the 5th column holds the default gamepad key as an Unreal FKey name (Gamepad_LeftX, Gamepad_FaceButton_Bottom, Gamepad_LeftStick_Up ...), which pins the action to that control (XboxControls.FromUnrealKey).
  5. Writer (only when the file is understood): keep unknown lines, the game's type codes and unbound markers, write only while the game is closed, back up first (GameExportSafety), write every profile variant, check after one launch that the game or a cloud copy did not undo it. Games that store gamepad binds implement IGameGamepadBinds and get their binds on EngineVJoy.XboxDeviceName with XB_* inputs in Xbox mode.
  6. Virtual mode: engine vjoy mode <game> virtual|xbox; the planner places the inputs and lists what does not fit; HidHide hides the real devices from the game only.
  7. Anti-cheat note per game (Javelin, EAC, BattlEye): JoyPro only uses signed virtual drivers (vJoy, ViGEmBus) and HidHide, no injection.
  8. Re-import: the virtual binds map back to the physical inputs through the stored table.
