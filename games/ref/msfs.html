MSFS 2024 in short: the sim takes JoyPro's preset package only for aircraft it has no own settings for that device yet. It also makes such settings without a flight, so aircraft you never flew can have them already (a test PC, 2026-11-01: settings for 56 aircraft, none flown). For every other aircraft, use your own profile (the export writes it) or the import file JoyPro writes per device: Settings > Controls > device > category > cogwheel of the profile > Import (see "Getting the binds into the sim").

#Two games: MSFS 2020 and MSFS 2024

JoyPro handles the two sims as two games side by side (both can be installed; a test PC has both on Steam):

MSFS 2020 (MSFS2020) MSFS 2024 (MSFS2024)
CLI engine msfs2020 (fs2020) engine msfs2024 (fs2024; old name msfs)
Install Steam app 1250410 (FlightSimulator.exe), Store Microsoft.FlightSimulator_8wekyb3d8bbwe, %APPDATA%\Microsoft Flight Simulator Steam app 2537590 (FlightSimulator2024.exe), Store Microsoft.Limitless_8wekyb3d8bbwe, %APPDATA%\Microsoft Flight Simulator 2024
Export target (paths) the Steam remote folders of app 1250410 (inputprofile_*); the Store version's profiles are imported, not written JoyPro's preset package Community2024\joypro-input-profiles, then the Steam remote folders of app 2537590; the export to the package also writes your own profiles the sim uses (Steam remote folder or Microsoft Store save, see "Writing your own MSFS 2024 profiles") and import files where those cannot be written (Documents\JoyPro2\MSFS 2024 import files (2.2.7: Documents\JoyPro, moved at the next export), see "Getting the binds into the sim")
Process (export refused while it runs) FlightSimulator FlightSimulator2024
Catalog DB\MSFS2020\actions.tsv DB\MSFS2024\actions.tsv
Aircraft list DB\MSFS2020\aircraft.tsv (44 aircraft on a test PC) DB\MSFS2024\aircraft.tsv (81)
refresh-db reads MSFS 2020's presets (<install>\Input, its Official packages) and locPak MSFS 2024's presets (fs-input-profiles, asobo-input-profiles-pc) and locPak

Both use the same code (engine\Games\MsfsIntegration.cs, one instance per sim) and file reader, so either game still reads and writes a profile file or folder of the other sim's format when it is given with --path. The axis model is msfs for both (tuning scopes game:MSFS2020, game:MSFS2024, and family:msfs for both). Both catalogs started as the shared catalog of the single MSFS game (built from both sims' data); each refresh only adds its own sim's actions. The aircraft lists come from the same discovery (both sims are read: a streamed 2024 aircraft takes its title from the same 2020 package), each game keeps the aircraft of its sim.

Profiles and settings saved before the split (game MSFS) are migrated when they are loaded (engine\Games\LegacyGameIds.cs): a node MSFS:<action>[:<aircraft>] becomes an MSFS2024 and an MSFS2020 node with the same aircraft; game:MSFS tuning becomes family:msfs. A folder set for "Microsoft Flight Simulator" in Settings > Games goes to the sim it belongs to (FlightSimulator.exe, 1250410 or the 2020 Store package -> 2020, else 2024), "I do not have MSFS" hides both. engine msfs ... and --node MSFS:<action> still work (MSFS 2024, and a node per sim). Ownership data and backups stay in %LOCALAPPDATA%\JoyPro2\Ownership\MSFS / Backups\MSFS (kept per file path). The watcher's records (<data>\Sync\MSFS.json) are not carried over; the next export records each sim again.

#Files

  • 2020 Steam: <Steam>\userdata\<id3>\1250410\remote\inputprofile_<10 digits> (XML, no extension). profile_00 (binary) maps device instance GUIDs to the inputprofile files. Steam Cloud folder.
  • 2020 MS Store: %LOCALAPPDATA%\Packages\Microsoft.FlightSimulator_8wekyb3d8bbwe\SystemAppData\wgs\... containers; blobs are renamed on every save. Read only (imported, see below).
  • 2024 Steam: <Steam>\userdata\<id3>\2537590\remote\inputprofile_*. 2024 Store: Microsoft.Limitless_8wekyb3d8bbwe\SystemAppData\wgs\.... Both are written by the export since 2026-10-20 (the profile the sim uses per device and category, see "Writing your own MSFS 2024 profiles").
  • 2024 supported route: Settings → Controls → cogwheel → Export/Import (same controller and same category only). [SRC MS support]
  • 2024 JoyPro route: Community package (engine\Games\MsfsCommunityPackage.cs). MSFS 2024 loads device presets from packages; Asobo ships the presets of known sticks that way (<install>\Packages\asobo-input-profiles-pc, fs-input-profiles). Each preset is plain XML under InputProfiles\Categories\<Airplane|Glider|Helicopter|LighterThanAir|Other|Transversal>\ with root <DefaulftInput Primary="1" PlatformAvailability="PC"> and <Device DeviceName GUID ProductID="C215" CompositeID HWVer>. The sim matches a preset to a device by the USB product ID (hex). A preset lists only the bound actions. The package also has layout.json (every file with size and FILETIME date) and manifest.json (package_order_hint: INPUT). The exe confirms the folder rules (InputProfiles/Categories/<Category>). [OBS, SRC SDK "Input Profiles"]
    • JoyPro writes <packages>\Community2024\joypro-input-profiles\InputProfiles\Categories\Airplane\JoyPro_<device>_<guid8>_2024_Planes.xml per device, then layout.json and manifest.json (builder: Microsoft Flight Simulator 2024). <packages> is InstalledPackagesPath in %APPDATA%\Microsoft Flight Simulator 2024\UserCfg.opt (Store: ...\Microsoft.Limitless_8wekyb3d8bbwe\LocalCache\UserCfg.opt). Community2024 is the folder for packages built for 2024: the sim's session report (AsoboReport-RunningSession.txt) counts a package there under communityfolderfs24, and the same package in Community under communityfolderfs20. The config path for msfs export|import|scan is the Community(2024) folder or the package folder (engine msfs2024 paths lists it).
    • General binds (since 2026-10-19): a device with binds of the general contexts (cameras, views, active pause, ...; the sim's "General" page) also gets ...\Categories\Transversal\JoyPro_<device>_<guid8>_2024_Transversal.xml, the folder Asobo's own presets use for them (asobo-input-profiles-pc\InputProfiles\Categories\Transversal\*_2024_Transversal.xml, no <AircraftInfo>, contexts such as COCKPIT_CAMERA, EXTERNAL_CAMERA, MODES, INGAME_UI, VIEW_MODE_SWITCHES). The exe names the category folders Airplane, Glider, Helicopter, LighterThanAir, Other, Transversal ("... must be either ..."). General actions go only into the Transversal preset, flight actions only into the airplane preset; each keeps its context (the action's catalog category).
    • Encryption (since 2026-10-19): the package matches the EFS encryption of the Community folder it is in. A Microsoft Store install on another drive keeps its data encrypted (EFS), and Windows refuses a plain file there: "The APPX file can not be accessed because it is not encrypted as expected." (409, an EFS refusal; report on 2.2.1, MSFS 2024 Store). JoyPro 2.1.1 to 2.2.1 removed the mark from the package before every export (meant for the 6000 case below), which caused it. Now the export never removes the EFS mark of the package; when the Community folder is encrypted it first repairs the package (MsfsCommunityPackage.MatchFolderEncryption / SafeFileIo.MatchFolderEncryption): File.Encrypt (EFS) on every folder and file that lost the mark; a file Windows does not EFS-encrypt is read, deleted and written again (it takes the folder's mark); a file that cannot even be read is moved to <data>\Backups\MSFS\package-<time> (deleted when that fails) and the export makes it again (a warning names the device presets that were reset; the binds come from the JoyPro profile; earlier copies are in JoyPro's backups). New preset files are written into the folder and take its mark. Everything done is logged (MSFS log area). Not verified on a real Store install on a second drive (no such PC); the simulated EFS states are covered by SafeFileIoTests, real EFS by the opt-in JOYPRO_TEST_REAL_EFS=1.
    • When Windows cannot EFS-encrypt a folder (2.2.5 report, MSFS 2024 Store): File.Encrypt (EFS) failed on every package folder with "The request is not supported.", so each export deleted the unreadable presets and wrote them again into folders without the EFS mark: plain again, unreadable again (409) for the sim and JoyPro (the export then found "no MSFS profile of device ..."). The preset files made while the folders still had the EFS mark stayed readable, so a new file or folder made in an EFS-encrypted folder takes its EFS mark there. Now such a folder is made again (SafeFileIo.RebuildFolder): a new folder beside it (checked: it must carry the EFS mark, else nothing changes), EFS-encrypted files moved over (they keep their EFS mark), readable plain ones written into it, unreadable ones moved out of the way as before, then the new folder takes the old name. Files in a folder without the EFS mark are no longer deleted and written again (it would not help). What still fails is a warning that says to delete the package folder with the sim closed and export again (EFS: the folder made then takes the Community folder's mark). The step "encrypted (EFS) again" counts only what worked. Test: SafeFileIoTests.MatchFolderEncryption_FoldersWindowsCannotEncrypt_AreMadeAgain.
    • Import of an own preset Windows cannot read (EFS, 409): the import first tries File.Encrypt (EFS) on it; else it reads JoyPro's newest readable copy (<data>\Backups\MSFS\<file>.<time>.jpbak, made by an export before it writes the file, or <data>\Backups\MSFS\package-<time>\<file>) with a warning: the sim does not use the file either (no EFS mark), the binds come from the copy, export once to write it again. Without a copy the warning says that its binds were not imported and to import with "Merge into profile" (not --replace), then export. The device is not taken as "no own profile" when the copy was read (no default preset over it). Test fault: JOYPRO_TEST_FAULT_ENCRYPTION=read:409:<file name> (simulated EFS refusal); test MsfsProfileImportTests.Store2024_PresetsTheSimsRecordsDisagreeOn_AreNotImported_UnreadableOwnPresetFromJoyProsCopy.
    • Product ID: the one the sim noted for the device in profile_00 (read only), else the USB PID. The sim sees vJoy as product ID 0 (not 0xBEAD); real sticks match their USB PID (WINWING 0xBE04, VKB 0x0125).
    • Axis settings go into each action as a per-action override (flag 4096 + <Axis/>): the sim ignores a preset's <Axes> block. The device page (Hardware Settings) stays per device.
    • No DeviceConfig.xml: an entry without a display name renamed the device to "Unknown Device" in the sim.
    • A device needs its product ID, so it must be connected for the first export. The preset is created once and reused. New actions go into their catalog context.
    • When the sim uses the preset (in-sim check 2026-10-10): the sim keeps one record per device and aircraft in profile_00 and fills it with the device's default preset when it creates it (first time that device is configured for that aircraft). The vJoy test preset showed exactly the exported random binds for an aircraft the sim had not configured yet (Cessna 185: flaps down button 7, rudder RAXIS Y, ailerons LAXIS Y, elevator RAXIS X, nav lights button 13). For an aircraft already configured with that device the old record stays (empty or the previous preset). Only Controls > Reset to Defaults (End) re-applies the defaults, and it resets the presets of every device and aircraft ("Your custom profiles will not be deleted"), so JoyPro does not do it.
    • JoyPro never edits profile_00: the file ends with a checksum, and a changed file made the sim discard the whole profile (new profile_00, "Connect to Xbox Network" with account linking on the next start). The original file put back fixed it.
  • Getting the binds into the sim (since 2026-10-19, 2.2.6 report, MSFS 2024 Store): "MSFS does not recognise any new relations generated from JP": relations made in JoyPro never showed up in Controls. Cause: the package preset applies only where the sim has no record yet (above), and the tester's profile_00 (read only, copy) has records for every connected device in every aircraft he flew: VMAX throttle, MOZA AB9, Total Controls MFBB and VPC Panel #2 with his own profiles (slot flag 3, inputprofile_<n>) or with no preset, the T-Pendular-Rudder on its shipped preset, the MFDs on theirs. So JoyPro's presets reached only aircraft he had never used with a device. The Store keeps his own profiles in its save containers, which JoyPro did not write before 2.2.9 (now it does: "Writing your own MSFS 2024 profiles").
    • Import files (engine\Games\MsfsIntegration.ImportFiles.cs): every export to the package (not a dry run) also writes, per device and category with binds, a profile in the sim's own format into Documents\JoyPro2\MSFS 2024 import files (<JOYPRO_DATA_DIR>\MSFS 2024 import files when set): <device>_<guid8>_Airplanes.xml / _General.xml. Base: the user's newest own profile of that device and category (Steam remote folder or Store save, read only), so his other binds and the listing stay; JoyPro's binds go in by the export mode and ownership (kept per import file). Without an own profile: a new profile (<Version Num="-1"/>, <FriendlyName>, <Device DeviceName GUID ProductID> with the decimal product ID the sim noted or the USB PID, <AircraftInfo CategoryName="AIRPLANE"/> for airplanes) listing every action of the command list for the category. The name is "JoyPro Airplanes|General". A step per file says what the sim does with the device now (from its records: "the sim keeps its own settings of this device for N aircraft ... import this file"), and the export ends with the steps: Settings > Controls, pick the device and the category (Airplanes or General), the cogwheel of the profile (not the preset's; tester report on 2.2.7) > Import, pick the file (the sim imports only a file of the same device and category). A step lists the files that are new or changed since the last export (only those need importing again). The GUI (Other Games, Export) shows the folder with "Open folder" and these steps. Test: MsfsProfileImportTests.Store2024_Export_WritesImportFilesPerDeviceAndCategory (Store save unchanged, dry run writes none).
    • Since 2026-10-20 the export writes the user's own profiles (next section); the import files are written only for a device and category JoyPro could not update there (--import-files / GUI "Also write MSFS import files for every device": always). An import file of a device whose active profile JoyPro knows carries that profile's name (<FriendlyName>): the sim's Import then asks "a profile with that name already exists, overwrite?" and Yes puts the binds into the user's profile (tester finding, MSFS 2024 Store; Import creates a new "JoyPro ..." profile otherwise). The step says so ("Import it and confirm 'overwrite': your profile 'X' then has JoyPro's binds"). Every bind goes into the category the sim lists its action in (the user's own profiles list every action of their contexts: KEY_ACTIVE_PAUSE_TOGGLE is in INGAME_UI, a General bind, also when the shared command list has it in PLANE from MSFS 2020; tester report "Active Pause not in the sim"), and the file is read back: a bind that did not land is named ("not written: () (General) - "). - Not verified in the sim: that its Import takes these files (format as its own profiles and exports; the menu path from the MS support article and the in-game help); not checked on a real Store install.
    • Re-import of JoyPro's own relations: relations made before 2.2.6 ("Microsoft Flight Simulator 2024 ") are matched by node, not by name: an import into such a profile (tester's copy, 28 relations) added only the 2 new binds and kept every old name.
  • 2024 profile_00 (Steam remote): a binary tree. A node is an 8-byte name hash, a uint32 size (header included) and a payload: a container holds a uint32 count and child nodes, a leaf holds a value (strings NUL-terminated). 2020 uses the same format. The tree holds:
    • a device table (instance GUID string, type);
    • per device, the category scope (AIRPLANE) and the aircraft scope (asobo-aircraft-c172sp-as1000);
    • per device and aircraft, three preset slots (general = transversal, category, aircraft), each with the preset file name (keyboard_2024_planes.xml; empty = none). [OBS 2026-10-10]
    • field hashes (2026-10-19, engine\Games\MsfsSimProfile.cs): instance GUID e494a07827809546 (string; keyboard and mouse a number), type c5e29153ab70ce33 (1 joystick, 15 keyboard/mouse), product ID 9c6a107054980963, composite ID 419c4be1028db14a, preset file e5374a443ee0986e, category dd0e07ae6ad0a4fc, aircraft 6ef48b11820c125d; slots ae7f5b37a56a781c (general), 8b57821791389404 (category), 6bc4c835749736a7 (aircraft) inside a record that carries the device fields itself. The file ends with 5 bytes after the tree.
    • more fields (a tester's Store profile_00, 2026-10-19): slot flag 00d10becc027d54f (0 none, 1 shipped preset, 3 own profile: the preset field then holds inputprofile_<n> and the name field its name), display name 877ddf5aa523fd04 (the preset's name, "TT:GENERIC.NONE" for none; often empty, also for the keyboard on the test PC's Steam copy, so it is not used), aircraft path a8df1050ac9f14e5. Under the root container a532ec6925941962: a46c8bf66a7db8ce (per device a general entry), 4f1fd58aaa70b44e (per device and category), 7af6b80fdb235d3f (per device and aircraft) all with empty preset fields on both PCs, and a9281cff465213e7 (the records, one per device and aircraft configuration). Old device instance GUIDs keep their records.
  • 2024 in-game observations (Steam, 2026-10-10, menus only):
    • The Steam remote folder holds only profile_00, localprofile and datausage (binary), and no inputprofile_*, until a preset exists. No XML profiles under %APPDATA%\Microsoft Flight Simulator 2024.
    • A device without a preset (vJoy) shows no preset selector and no preset gear. Its device gear only offers Rename / Deactivate / Hardware Settings, so there is nothing to export until one bind creates a preset.
    • The help page says: preset management is the gear next to the preset selection; binding = select the action, click an empty slot (shows "Scanning..."), then move the axis.
    • The scan takes the first input of any device. A device that keeps sending (a VPforce Rhino FFB stick: the Control listener shows SLIDER X/RX changing with nobody touching it) makes the slot show "WRONG DEVICE", and the bind never happens.
    • Hardware Settings (device gear) = device-level curves per axis (Sensitivity +/-, Neutral, Dead zone, Extremity Dead Zone, shown as 0.00) with a live dot on the curve: a menu-only way to check curves without a flight.
    • Per-action settings (row gear): input repetition, delayed input, set on release, inverted axis, current axis value, input value override, device input curve override, tweak action curve.
  • Default device profiles: <install>\Input\*.xml.
  • Cloud (Steam, Xbox, 2024 server) can revert local edits. New inputprofile_* files are not picked up (profile_00 references specific files): only edit existing ones.

#Writing your own MSFS 2024 profiles (since 2026-10-20)

Tester (MSFS 2024 Microsoft Store): importing JoyPro's file in Controls worked but made a second profile "JoyPro Airplanes"; his default profile should have the binds. The export (engine\Games\MsfsIntegration.UserProfiles.cs) now writes the profile the sim uses for every device and category of the export; --user-profiles false (GUI: "Write into my MSFS profiles", on by default, remembered in export-settings.json) turns it off. JoyPro's package presets stay (they reach aircraft the sim has not set up for a device yet).

#Devices

GUID = DirectInput instance GUID (machine specific), ProductID = decimal PID, CompositeID for multi-part devices. Keyboard/mouse GUID="{0}". One profile file per device and profile.

#Flight contexts [SRC Input_Profiles]

AIRCRAFT, BASIC_CONTROL(_HELICOPTER/_LIGHTER_THAN_AIR), INSTRUMENTS_CONTROL, PLANE, HELICOPTER, GLIDER, LIGHTER_THAN_AIR, RUDDER_AXIS, SURFACES(_HELICOPTER/_LIGHTER_THAN_AIR), THROTTLE; 2024 also AIRCRAFT_PC, SURFACES_GYRO, AIRCRAFT_ACTIVE_INTERACTION, HELICOPTER_ACTIVE_INTERACTION. Everything else (cameras, MENU, MODES, DRONE, SLEW, DEBUG, ATC) is general.

#Managed contexts (since 2026-10-19)

Until 2.2.1 JoyPro read and wrote only the flight contexts; a tester's cockpit view zoom axis, view toggles and active pause (the sim's "General" page) were not imported. Now JoyPro manages every context except the sim's own navigation and developer ones (MsfsIntegration.IsManagedContext):

  • Left alone: MENU, MENU_* (menu navigation), WORLDMAP_* (world map), DEBUG, DEVMODE*, EDITOR_* (developer mode and its editors), MISSION_FLOW_TOOLS. They are UI navigation and debug binds, not the user's flight setup; import counts them ("bind(s) in menu, world map and developer contexts left out"), export never changes them (also not clean/nuke: the import leaves them out, so a round trip keeps them).
  • General (managed): everything else outside the flight contexts, e.g. ALWAYS, ATC, COCKPIT_CAMERA, COCKPIT_GLOBAL_CAMERA(_TRANSLATE), COCKPIT_INTERACTIONS(_LOCK), CURSOR(_MODE_SWITCHES), DRONE(_GLOBAL), EFB(_CORE), EXTERNAL_CAMERA, FIXED_CAMERA, HANGAR_CAMERA, INGAME_UI, INSTRUMENTS_CAMERA, MODES, MODE_PAUSE, PC_MODE_SWITCHES, PHOTO_MODE_*, PLAYER_CHARACTER_*, SIM_SHORTCUT, SLEW, SMART_CAMERA, TOOLBAR, USER_CAMERA, VIEW_MODE_SWITCHES (the contexts of Asobo's 2024 Transversal presets, checked 2026-10-19; real 2020 profiles bind KEY_COCKPIT_CAMERA_ZOOM_AXIS in COCKPIT_GLOBAL_CAMERA). A new context of a later sim is managed too.
  • Export writes a general action into its context: 2020 / Steam profiles in place (the context the action has in the folder's profiles, else its catalog category), 2024 package presets into the device's Transversal preset (see above). Ownership, merge rules and backups are the same as for flight actions.

#Action list

2024 profiles list every action of their contexts (unbound ones as empty <Action/>). 2020 profiles only hold bound actions: seed with the SDK Event IDs (KEY_ + name).

#JoyPro implementation (engine msfs2020 ..., engine msfs2024 ...)

  • Config path: one profile file or a folder (Steam remote folder of 2020/2024, or a folder of 2024 exports). engine msfs2020 paths lists the 2020 Steam folders, engine msfs2024 paths the 2024 package and Steam folders; both also list the Microsoft Store save folder (...\SystemAppData\wgs) when there is one. Import reads the Store profiles of both sims. MSFS 2020's Store profiles are never written. MSFS 2024's are written by the export to the package (the profile the sim uses per device and category, --user-profiles, see "Writing your own MSFS 2024 profiles"); the Store save folder itself is refused as an export path in both sims.
  • 2024 workflow: run engine msfs2024 export <Community folder> (GUI: the discovered package path) with the sim closed: it writes JoyPro's presets into the package and your binds into the profiles the sim uses (Steam remote folder or Microsoft Store save). Only for a device and category JoyPro could not update there (or with --import-files for all of them, --user-profiles false for none), import the files of Documents\JoyPro2\MSFS 2024 import files in Controls (see "Getting the binds into the sim"). The old route still works for an exported file: Controls > cogwheel > Export, engine msfs2024 export <file>, then Import in the sim. 2020 Steam: edit the remote folder with the sim closed.
  • Device = the GUID attribute (DirectInput instance GUID), so no connected device is needed; keyboard/mouse profiles (GUID="{0}") are skipped.
  • One profile per device (and 2024 category) is used: the one picked with --game-profile <FriendlyName>, or the only one. Devices with several profiles are skipped with a warning listing their names.
  • Written: only actions in managed contexts (flight and general, see above) and in the catalog; only changed <Action> elements are re-rendered. Axis binds set flag 4 and 128 (invert) and the axis settings below; a released 2024 action becomes an empty element again, a released 2020 action is removed.
  • KEY codes: buttons N-1, first hat up/right/down/left 256-259 (no diagonals), full axes X/Y/Z 1026/1042/1058, Rx/Ry/Rz 770/786/802, sliders 514/530. The last KEY of a combination is the main input, other buttons of the same device are modifiers; axes take no modifiers. Half axes are not read.
  • New actions: 2024 files already list all actions of their category (an action no profile of the device holds, e.g. a General bind of a device without a Transversal profile, is reported once and skipped); in 2020 files the action is added to the context it has in the other profiles of the folder, else (general actions) its catalog context, else PLANE (with a warning). JoyPro's 2024 presets: general actions into the Transversal preset, flight actions into the airplane preset.
  • Primary/Secondary: at most two input combinations per action; a third is reported and skipped.
  • Export modes: only add writes a bind only where the profile has no other action on that combination (else it is listed under "Binds Not Written, Button Taken In The Game") and changes no bind that is there; merge replaces a combination the profile gives another action (the conflict) and keeps everything else, also a moved action's old combination (two slots per action); merge-overwrite also takes the actions the export binds off their other combinations in the profiles of connected devices; clean keeps only the export's binds in the profiles of the connected devices it writes, nuke clears the profiles of connected devices without binds. Profiles of devices that are not connected and the menu, world map and developer contexts are never cleared. Ownership (device axis pages only) and backups live in %LOCALAPPDATA%\JoyPro2\Ownership\MSFS and ...\Backups\MSFS, never in the Steam-synced folder. clean only changes profiles of devices that JoyPro binds in the export. The backups copy the bytes (SafeFileIo) into JoyPro's own folder: a Store-version export failed with "The specified file could not be encrypted." (2.1.0 report) when File.Copy tried to keep a preset's EFS encryption. JoyPro's package keeps the EFS encryption of its Community folder (2.1.1 to 2.2.1 removed it, which broke Store installs on another drive with error 409; see "Encryption" above and backups).
  • Catalog: DB\MSFS2020\actions.tsv and DB\MSFS2024\actions.tsv (each started as the same list: flight-context actions of MSFS 2024 airplane + helicopter exports and MSFS 2020 profiles). Input actions belong to contexts (AIRCRAFT, HELICOPTER, GLIDER, ...), not to an aircraft: a 2024 export lists every action of its contexts whatever aircraft is loaded, so the catalog is not tied to the test aircraft (Cessna 185). Axis actions are recognized by name (AXIS, *_SET of throttle/mixture/prop/surfaces).
  • Refresh from the game: engine msfs2020 refresh-db / engine msfs2024 refresh-db (no path; GUI: Games > DB refresh without a source) reads the sims' own data, read only (engine\Games\MsfsGameData.cs): the device presets Asobo ships (MSFS 2024 <install>\Packages\fs-input-profiles and asobo-input-profiles-pc, InputProfiles\**\*.xml; MSFS 2020 <install>\Input; Store installs under the InstalledPackagesPath of UserCfg.opt, Official*\*) and adds every action of a managed context they bind, with its context (since 2026-10-19 also the general ones of the Transversal presets and the user's General profiles: cameras, views, pause, ...; an action the list has in a flight context that this sim binds in a general one moves to it; since 2026-10-19 also JoyPro's own package presets, and the context the user's 2024 profiles list an action in corrects one the list has from elsewhere; general events only the locPak names: see "General events only the locPak names" below); new actions get the Controls menu name from fs-base\en-US.locPak (INPUT.KEY_...), known ones keep their title (import names relations after it) unless it is the raw event name (below). --path <folder> reads exported profiles instead. Readable titles (since 2026-10-12): the locPak writes the menu names in capitals; the catalog takes them in title case (ELEVATOR AXIS -> Elevator Axis, THROTTLE 1 AXIS (-100 to 100%) -> Throttle 1 Axis (-100 to 100%); the panel abbreviations stay: AP, NAV1, ADF, VOR, TACAN ...). A known action still titled by its raw event name (AXIS ELEVATOR SET, the lists built before) is renamed too; every other known title stays. Without a locPak name (no locPak found, or an event it does not list) the title comes from the event name: KEY_AXIS_ELEVATOR_SET -> Elevator Axis, KEY_THROTTLE1_AXIS_SET_EX1 -> Throttle 1 Axis (MsfsGameData.Readable / TitleFromEventName). The ids do not change, so relations, binds and exports are untouched; only relations made by a later import are named after the new title. The lists already on a PC get the readable titles with the next refresh-db (GUI: Games > DB refresh); nothing is renamed on load. Where the locPak is: Steam <MSFS 2024 install>\Packages\fs-base\en-US.locPak (2.2 MB, 2026-10), MSFS 2020 %APPDATA%\Microsoft Flight Simulator\Packages\Official\Steam\fs-base\en-US.locPak (the InstalledPackagesPath of UserCfg.opt). Fresh build on a test PC (2026-10-12, temp data folder): MSFS 2024 1715 menu names + 52 from the event name, MSFS 2020 1555 + 201. Every search hit carries the event id next to the title (Id); the relation editor finds the primary flight axes first (docs/relation-builder.md "Primary axes"). Since 2026-10-12 the refresh also adds every flight event the locPak names but no preset binds (most aircraft systems: autopilot, radios, lights, fuel, engines, G1000 and GPS keys, breakers, ...), so a fresh install does not depend on the user's exported profiles. The locPak names each event but not its context, so JoyPro's own rules decide (MsfsGameData.IsFlightEvent / GuessContext): not flight are cameras, views, menus, UI, developer mode, debug, photo mode, xCloud, slew, EFB, toolbar, ATC, cursor, VR, replay, multiplayer, the on-foot character, failures and blockages, recording; the context is LIGHTER_THAN_AIR (airship, balloon, burner), HELICOPTER (heli, rotor, collective, cyclic, auto hover), GLIDER (water ballast, tow plane), PLANE (the plane-only systems of the presets: liquid dropping, grapple hook, skydive lights, G limiter, ...), else AIRCRAFT. Fresh build on a test PC (2026-10-12): MSFS 2024 1739 actions (presets 360 + 1379 named), MSFS 2020 1580; of the development list (from real exports) 1343 / 1195 ids are rebuilt, and the guessed context matches it for 91 % of the locPak-only events (most others are MSFS 2020 INSTRUMENTS_CONTROL rows of the shared development list). Check 2026-10-10 (2024 build of 2026-10-04): the 720 presets of both sims bind 1197 actions; every flight-context one was already in the catalog except 4 MSFS 2020 PLANE actions (back to fly, flashlight, pushback, UI window mode), now added. The locPak names 2736 KEY_ events; most of the rest are camera, menu, debug, VR and SimConnect-only events (e.g. KEY_AXIS_THROTTLE_SET; the 2024 Controls menu offers KEY_THROTTLE_AXIS_SET_EX1). General events only the locPak names (since 2026-10-19): with a full General profile of the user read (it lists every general action the sim offers) they stay out: the sim's menu does not offer them. Without one (a fresh install, Steam with no own profile) an event joins with the context of the known general actions sharing at least its first two name words, when two thirds of them agree (KEY_INSTRUMENT_LOOK_UP -> INSTRUMENTS_CAMERA like KEY_INSTRUMENT_LOOK_DOWN; MsfsGameData.GuessGeneralContext), else it stays out. Checked against a full General listing of a tester's profile: of the 720 general events only the locPak names, 490 sit in the sim's debug contexts, 170 in managed ones; the rule places 63 right and 14 wrong (mostly debug ones), the rest stays out; an import of a General profile later corrects a wrong guess. Counts (2026-10-19): a test PC's Steam install without own profiles: development list 1378 -> refresh 2165 before, 2420 now (ATC Panel Choice 0 ... 9 in both); with the tester's 18 Store profiles 2398 (no guesses: his General profile lists everything). #Aircraft lists (DB\MSFS2020\aircraft.tsv, DB\MSFS2024\aircraft.tsv, engine\Games\MsfsAircraft.cs)

engine msfs2020|msfs2024 refresh-db (with or without --path; GUI: Games > DB refresh) also lists the installed aircraft of both sims, read only, and merges the aircraft of its sim (column sims) into its DB\<MSFS2020|MSFS2024>\aircraft.tsv (aircraft found before stay, like the DCS planes; the file ships with JoyPro as DCS's plane list does, and is written only when it changes, never on --dry-run).

  • Identity (key) = the aircraft's package name without the fs20-/fs24- prefix of the 2024 content list, e.g. asobo-aircraft-c172sp-as1000. [OBS 2026-10-10/11] MSFS 2024's profile_00 keeps its device x aircraft input records under exactly these names (asobo-aircraft-c172sp-as1000, microsoft-aircraft-c185f-skywagon for the streamed packages fs24-asobo-aircraft-c172sp-as1000 / fs24-microsoft-aircraft-c185f-skywagon; read only from a copy). An MSFS 2020 package has the same name (Official\Steam\asobo-aircraft-c172sp-as1000), so one key covers both sims. One package can hold several SimObjects (floats, skis): they share the key (the 2024 record is per package too). [INF] For fs20- packages that 2024 runs, and for Community packages, the record name is assumed to follow the same rule.
  • Sources:
    • Package folders with manifest.json content_type AIRCRAFT (liveries are LIVERY and are left out, as are packages without an aircraft SimObject such as *-gliders-common): <InstalledPackagesPath>\Official*\<store>\*, Community, Community2024 (UserCfg.opt of 2020 and 2024, Steam and Store) and <install>\Packages. Title = the manifest title (what the content manager shows), manufacturer = manifest manufacturer (else the cfg's icao_manufacturer). aircraft.cfg: SimObjects\<cat>\<obj>\aircraft.cfg (2020) and the 2024 modular files (...\common\config\aircraft.cfg, ...\presets\<creator>\<preset>\config\aircraft.cfg); a cfg with [VARIATION] base_container is a livery. [GENERAL] category (airplane/Helicopter; MSFS 2020 lists its gliders as airplane) and icao_type_designator; the user-selectable [FLTSIM.N] titles (isUserSelectable=0 = AI traffic) are the variants (the sim's TITLE). Packed packages: the aircraft.cfg paths in layout.json (category from the SimObjects folder: Rotorcraft = helicopter).
    • MSFS 2024 streams its aircraft: Official2024\Steam is empty and StreamedPackages\<package> holds only cached .fsarchive parts, so there is no readable aircraft.cfg. The owned packages are listed in the content list <UserCfg folder>\<id>\Content.xml (<Package name="fs24-asobo-aircraft-c152" active="Activated"/>, also UserDisabled / SystemDisabled). JoyPro takes the activated -aircraft- packages that are no livery, no AI traffic (passiveaircraft), no base or shared package (fs-base-*, *-common, simattachmentlib, trainings, efb-app). Their title comes from the same package of MSFS 2020 when it is installed, else it is derived from the package name (C185F Skywagon; column title source = package name) and the category stays empty. Without a content list the StreamedPackages names are used.
  • Format (tab separated, # comments): key, title, category, sims (2020,2024), icao type, manufacturer, packages (|), variants (|), title source (manifest | aircraft.cfg | package name).
  • Check 2026-10-11 (this PC, real refresh into a temp DB copy): 91 aircraft, 44 from MSFS 2020 (534 Official\Steam packages, 55 of type AIRCRAFT: commons and liveries left out) and 81 from the MSFS 2024 content list (61 aircraft packages there are switched off); 34 are in both. 47 of the 2024-only titles are derived from the package name.
  • Planes in JoyPro: engine db planes --game MSFS lists MSFS (= all aircraft) and every key; the GUI's relation node plane picker shows them with title, category and sims. --node MSFS2024:<action>:<key> (MSFS2020: for 2020) (or relations item add|enable|disable ... --node MSFS2024:<action>:<key>) limits a relation to aircraft. A node without aircraft or with MSFS active is for all aircraft (unchanged for existing profiles). Auto Group and Auto Assign keep MSFS as one aircraft (MSFS, one input configuration for the whole game), because the export below cannot separate aircraft.

#Export of relations limited to aircraft

MSFS has per-aircraft input settings, but JoyPro cannot write them:

  • MSFS 2020: one input profile per device (inputprofile_*), used for every aircraft. [SRC docs above, OBS]
  • MSFS 2024: the sim keeps a record per device and aircraft in profile_00 with three preset slots (general / category / aircraft), and the exe knows General, CategoryAircraft, CommonAircraft and SpecificAircraftInputPresetForDevice presets [OBS: profile_00 copy, FlightSimulator2024.exe strings]. JoyPro never writes profile_00 (checksum: a changed file made the sim discard the whole profile). Aircraft-specific default presets come only with the aircraft's own package: the SDK puts them in an inputs folder beside attachments/common/liveries/presets of the aircraft's SimObject (SimObjects\Airplanes\<aircraft>\inputs), and the exe allows input profile asset groups only under InputProfiles, SimObjects or SimAttachments [SRC SDK "Aircraft Input Profile Package Setup", OBS exe]. Official aircraft are streamed, so JoyPro cannot add files to them. [INF, not tried] A Community package that overlays SimObjects\<cat>\<aircraft>\inputs of another package might be picked up, but it was not tested in the sim and could also break the aircraft's SimObject; JoyPro does not do it.
  • So the export (both sims) writes one set of binds per device for every aircraft: the relations for all aircraft, plus, with engine msfs2024 export --aircraft <key> (GUI: Other Games > Export Aircraft), the relations limited to that aircraft. Without --aircraft a relation limited to aircraft is skipped with a warning that says why; an unknown key is reported. The 2024 preset then applies as before: to every aircraft the sim has not configured for that device yet. The game config watcher (engine sync) compares the game files with the relations for all aircraft (as the export without --aircraft).
  • Verified: the export rules on synthetic 2020 profiles (smoke test). Not verified in the sim: anything per aircraft (no per-aircraft export exists to verify); the record names of fs20- and Community aircraft in profile_00.

#Axis settings (model msfs, engine\AxisModels\Msfs.cs)

The game's Settings > Controls > device > Sensitivity page (one set per physical axis of the device and profile) and the per-action options, in the file's units (the UI's percent; the UI code KeyCalibrationComponents.js/.html of the 2020 install has the ranges):

JoyPro key (binds tuning set --scope game:MSFS2024 --param ...) File Range
sensitivityPlus / sensitivityMinus (positive / negative half) AxisSensitivy / AxisSensitivyMinus -100..100 (UI slider -100..100 %; the SDK's "0..100" / "-100..0" is wrong: MS's own profiles have -50/-50)
neutral AxisNeutral -100..100
axisDeadZone AxisDeadZone 0..100
extremityDeadZone AxisOutDeadZone 0..100 (the UI slider also allows negative values)
reactivity AxisResponseRate -1 (off, default) or 100..2000 (the UI shows 0..100 %; the mapping is not known)
noSensitivityCurve (0/1) Flag bit 1024 the action gets the raw axis
axisOverride (0/1) Flag bit 4096 + <Axis .../> in <Action> before <Primary> the values for this action only (MSFS 2024)
Invert Flag bit 128
  • Import puts the values of the bound axis (the per-action <Axis/> when flag 4096 is set, else the device's line) into the relation's game:MSFS2020 / game:MSFS2024 tuning; only values that differ from the defaults, so an untouched page leaves none.
  • Export writes only what the tuning sets: a key it does not have keeps the file's value (a relation without MSFS values gets dead zone, extremity dead zone and sensitivity fitted from its base curve; neutral and reactivity stay). Lines are edited in place (other attributes and lines keep their bytes); a version-1238 line (AxisSensitivy, AxisDeadZone only) gets a missing attribute only when its value is not the default; a missing axis line is added in the sim's order (X, Y, Z, rX, rY, rZ, SliderX, SliderY) with the attributes the file's other lines use.
  • One page per device axis: relations on the same device axis share it. Different values are reported by binds tuning set and by the export, which writes the first relation's values. axisOverride=1 gives an action its own values (2024 profiles; in a 2020 profile the export warns and uses the device page). Without the key the export keeps the action's current override state and writes JoyPro's values where the game reads them for that action.
  • A released axis (or an action that becomes digital) loses flags 4/128/4096 and its per-action <Axis/> (it used to stay behind); flag 1024 and the other bits stay unless the tuning sets noSensitivityCurve.
  • The export warns when a changed device page also drives actions JoyPro does not manage (camera zoom etc.). Merge keeps a page changed in the game (not what JoyPro wrote or imported).
  • Preview, measured in MSFS 2020 (2026-10-10, tools\e2e\games\MsfsCurves.ps1: vJoy sweeps, SimConnect ELEVATOR POSITION / throttle lever; two runs with random pages, 84 points, max error 3e-4). With x the stick position and n = -neutral/100: the half x >= n uses Sensitivity -, the other half Sensitivity + (the sim works on the mirrored axis); a = |x - n|, h = the half's length (1 - n or 1 + n), d = dead zone/100: output 0 for a <= d, else v = (a - d)/(h - d) and y = (1 - e) * v(1+s)/(1-s+2sv) with s = sensitivity/100 clamped to +-0.99 (-100 = a step at the end of the travel) and e = extremity dead zone/100 (a cap on the output, not an early saturation). Flag 1024: the raw axis, but |x| <= d still gives 0 (not rescaled). Invert flips the result; THROTTLE_AXIS_SET_EX1 gets the value negated (full throttle at the stick's minimum). Reactivity is smoothing over time (not in the preview); its page slider shows (rate - 100)/19 %, -1 shows 100 %.
  • No force feedback: MSFS has none of its own (no DirectInput effects in either exe; FFB only through third-party telemetry apps); assistance options (assisted yoke, auto-rudder) are not in the input profiles. No FfbModels entry.
